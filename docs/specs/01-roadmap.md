# 拡張ロードマップ

## プロダクトの方向性

このプラグインは、まず Framer 向けの **カラーに特化したインポート兼監査ツール** として始めるべきです。

中核となる原則:

> ソース作成者が定義した構造と意図を壊さない。

これは次のことを意味します:
- プリミティブトークンを自動生成しない
- セマンティックトークンを自動生成しない
- 不足しているスケールを勝手に作らない
- ソース構造を暗黙に正規化したり統合したりしない
- ソースの命名、階層、エイリアス、意図をできる限り保持する

## ロードマップのレイヤー

### コア
- JSON カラートークンのインポート
- トークンの解析とバリデーション
- カラートークンのエイリアス解決
- ソーストークンを Framer で扱いやすいカラースタイル / 変数へマッピング
- プレビュー付きの安全なインポートフロー
- 基本的な競合処理
- インポート結果サマリー

### 隣接領域
- カラー監査
- 未使用スタイルの検出
- 直接指定されたカラー使用の検出
- セマンティックな文脈でのプリミティブ誤用の検出
- 命名一貫性の監査
- 重複カラーの検出
- テーマ網羅性チェック（ライト / ダークの完全性）

### 将来
- Radius トークン対応
- Shadow トークン対応
- Spacing トークン対応
- Typography トークン対応
- Motion トークン対応（duration / easing）
- スナップショットエクスポート
- ソース構造を保持したエクスポート
- チームガバナンス機能
- バージョン履歴 / 変更差分
- レポートとデザインシステム健全性ダッシュボード

## 推奨順序

### フェーズ 1
カラーインポートのみ

### フェーズ 2
カラー監査

### フェーズ 3
Radius と Shadow 対応

### フェーズ 4
Spacing 対応

### フェーズ 5
Typography と Motion 対応

## この順序にする理由

カラーには次の特徴があります:
- 直近のユーザー価値が最も明確
- インポートに関する痛みが最も強い
- MVP として扱いやすい複雑度
- 監査と組み合わせたときの差別化が明確

Radius と Shadow は比較的構造化されており、Typography よりも忠実に保持しやすいため、次に扱います。
